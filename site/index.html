Ripple

An always-on site engineer for Nav2 robots. It watches the robot, works out why it stopped, recovers within limits you set, asks a person when software can't fix what's happening on the floor, and gets better at each place it works.

What the demo shows

  1. Site control. A keepout drawn on the map is verified in the keepout mask and the global costmap. Nav2 plans around it, and Ripple verifies the arrival: stopped, within tolerance.
  2. Words become site state, then a failure. The walkway is reopened from a sentence. A pallet blocks the Home dock. Ripple reads diagnostics and logs, clears both costmaps, probes the route, then asks the engineer one question on Ambiguous.
  3. Human context. No one answered on Ambiguous in this run, so the reply was typed on the dashboard. Ripple locates the dock from the words, verifies a keepout over it, reroutes to the Charger and resolves on a verified arrival.
  4. The record. Ripple files the incident report to the team's Ambiguous workspace.
  5. A real reply on Ambiguous. In an earlier live run the engineer answers "check sensor data then use teleop". Ripple reads the scans, teleops 0.32 m clear, and retries the route home.

How it works

The model decides; the edge enforces. GLM 5.3 on OpenRouter only ever emits tool calls. Every call is validated and policy-checked by the edge, then journaled in PostgreSQL before it touches ROS. The robot's own safety controller stays above everything Ripple does.

Outcomes are verified, not assumed. A keepout counts once the published mask and the costmap show it. An arrival counts once odometry has settled and the pose is within tolerance. A recovery counts once odometry confirms the motion.

People are a channel, not a dashboard. Engineers talk to Ripple on Ambiguous, or on the local dashboard. An operator's message is the approval for what it asks: "send the robot to B" just runs.

One file per robot. ripple.json holds the robot's topics, safety controller, stations and recovery limits. A new robot is a new file, not new code.

Safety model

LevelExamplesWho decides
ObserveHealth, logs, diagnostics, route probesAlways allowed
RecoverClear costmaps, retry, navigate_via, lifecycle reset, bounded escape and teleopAutomatic within per-incident budgets
CommandNavigate, keepouts, station availabilityAn allowlisted operator's message is the approval
NeverRaw motor commands, shell, disabling collision checksNot exposed

The teleop safety override exists only on profiles that declare a simulation; the profile validator refuses it otherwise. Teleop never overrides an e-stop, and always stops inside its minimum clearance.

How it improves at one site

A robot works one site for months, and the same trouble comes back to the same corner. Ripple remembers what worked, without retraining a model. Every closed incident becomes a lesson for that place. A lesson holds:

  • the steps that led to a verified arrival;
  • the steps that did not help;
  • the steps the safety layer refused;
  • what the engineer taught.

When trouble happens nearby, the best lessons go into the model's briefing, so it tries what worked there first. Repeated trouble becomes a suggestion for a person, such as a keepout or a slow zone. Ripple never applies those changes itself.

The approach draws on ExpeL, ReasoningBank, CLIN, Agent Workflow Memory and Generative Agents. The guardrails come from the memory-poisoning literature:

  • lessons come only from outcomes the edge verified and from allowlisted people;
  • each one lists its evidence;
  • they are shown to the model as data, never as permissions;
  • people can list them and forget them.

Live, three incidents at one spot became one lesson with three successes, and recovery went from 45 s to 32 s to 30 s. Design and sources.

Set it up

git clone https://github.com/00PrabalK00/ripple && cd ripple
bash product/scripts/install.sh --workspace ~/robot_ws
ripple doctor --site ~/robot_ws/ripple.json
ripple run --site ~/robot_ws/ripple.json   # http://127.0.0.1:8060

ripple setup is a terminal wizard.

  1. It checks your OpenRouter key and your Ambiguous token live.
  2. It asks where Ripple should ask for help, and who may command the robot.
  3. It crawls the robot's workspace and the live ROS graph. Every topic, action and service is matched by message type and by the node that publishes or serves it, so different names on another robot don't matter.
  4. It asks you only about the fields it's unsure of.
  5. It writes one validated ripple.json, with secrets in a private .env, and runs ripple doctor.

Needs Ubuntu 22.04 and ROS 2 Humble. Node.js (for Ambiguous and the database bridge), Docker (for PostgreSQL) and Qt6Core (for RosScope) are optional. The simulator used is the external SMR300L Gazebo ROS2 Control, with two small patches from patches/.

Status and limits

  • Scope: one robot, in simulation. A second, stock-Nav2 profile runs with no code changes. Ripple has not been run on physical hardware.
  • Engineer replies: the Ambiguous reply loop works live. In the recorded full rehearsal, nobody answered in time, so that step fell back to the dashboard.
  • Localization: AMCL can lose track while the robot spins in a tight dock. Recovering from that still needs a person to re-seed the pose.
